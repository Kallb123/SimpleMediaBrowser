# Flutter Migration — Plan & Feasibility

*Investigation date: 2026-09-02 · Against `main` @ `432af56` (v2.2.0, versionCode 62, Expo SDK 55, RN 0.83.6)*

---

## TL;DR

**Technically viable, no dead ends — but it is a ~12,500-line rewrite with no
incremental path, and nothing in the current codebase is asking for it.**

| Question | Short answer |
|---|---|
| **Is there a blocker that kills it?** | No. Every native capability the app relies on has a Flutter equivalent (SAF, ACTION_VIEW handoff, thumbnails). One of them is worth ~50 lines of Kotlin rather than a dependency. |
| **Can it be done incrementally?** | **No.** This is the real cost. See §2.1 — there is no half-Flutter state you can ship. |
| **How big?** | ~12,500 LOC of real app code across 11 screens. Estimate **6–8 weeks full-time / 3–4 months at this repo's actual cadence.** |
| **Biggest risk?** | SAF. Flutter's SAF packages are small-community, not first-party. Expo's implementation is already de-risked against your users' real devices; a swap re-runs all of that. |
| **Does it get you iOS for free?** | **No** — and this is the argument worth killing early. See §2.6. |
| **Should you do it?** | On the evidence in this repo, **no.** Every concrete win listed in §5 is achievable inside the RN app for a fraction of the cost. |

The honest framing: this is not a *migration*, it is a **rewrite that happens to
target the same product**. The `docs/ios-port-feasibility.md` study describes a
3–4 week port because iOS shares the codebase. Flutter shares nothing but the
algorithms and the on-disk file format.

If the motivation is "I would rather work in Dart," that is a legitimate reason
and the plan below is real. If the motivation is a technical problem with the
current stack, §5 argues that problem is cheaper to solve where it is.

## 1. What actually transfers

Sorting the codebase by what survives a language change is the fastest way to
size this.

| Category | LOC (approx) | Fate |
|---|---|---|
| **Algorithms & data contracts** | ~1,500 | **Transfers as specification.** Mechanical translation. This is the valuable part. |
| Provider REST clients (`providers/`) | ~700 | Transfers — HTTP + JSON parsing, `http`/`dio` instead of `fetch`. |
| Scanner orchestration (`FileScanner.ts`) | 1,702 | Rewrite. Logic survives, every I/O primitive changes. |
| Redux slices + persistence | ~950 | Rewrite. Redux has no Dart equivalent worth emulating. |
| UI (11 real screens + components) | ~5,500 | **Full rewrite.** Zero transfer. |
| RN-specific plumbing | ~800 | **Deleted, not ported.** See §5. |

**The genuinely valuable IP is small and well-documented:** `normalizeShowName`,
`fuzzyKey`, `buildTmdbSearchQuery`, the season/episode parsing regexes, the
override key namespacing (`show:` / `movie:` / `episode:` / `audiobook:`), the
rescan carry-over rules (ARCHITECTURE.md §7 step 5), and the `smb.json` schema.

> **`smbVersion: 1` is an on-disk contract**, written into folders on users'
> drives and readable by the current RN build. The Flutter version must read and
> write it byte-identically. Do not "improve" the format during the port — that
> is the one change that would strand users mid-migration.

## 2. Blockers, ranked

### 2.1 There is no incremental path — **the defining constraint**

Flutter offers [add-to-app](https://docs.flutter.dev/add-to-app): a Flutter
module embedded in an existing Android host, screen by screen. That does not
apply here.

This is a **managed Expo CNG project with no committed `android/`** — it is in
`.gitignore` and regenerated by `expo prebuild`. Hosting a Flutter module means:

1. Ejecting from CNG (committing `android/`, losing config-plugin management),
2. Then maintaining React Native *and* Flutter *and* a bridge between them,
3. With shared state living on one side of that bridge.

For a single-maintainer hobby project that is strictly worse than either
endpoint. **Plan for a big-bang cutover on a branch**, with the RN app remaining
the shipping build until the Flutter one reaches parity.

The practical consequence: **there is no partial credit.** Six weeks in with
everything but Settings ported, you have shipped nothing. Every chunk below is
sequenced to keep verifiable value on the shelf anyway (see C0 and C2), but the
release itself is all-or-nothing.

### 2.2 SAF — the highest technical risk

SAF is not a feature of this app, it is the app's substrate. The scanner needs
exactly four operations, all confirmed available:

| Operation | Current (Expo) | Flutter |
|---|---|---|
| Pick a tree + persist the grant | `StorageAccessFramework.requestDirectoryPermissionsAsync()` | `saf` / `saf_util` — `pickDirectory`, `persistedPermissions()`, `hasPersistedPermission` |
| Recursive directory listing | `readDirectoryAsync` | `list()` / `walk()` |
| Read text & base64 | `readAsStringAsync` | `readFileStream` / byte reads |
| Create + write a file in a tree | `dir.createFile(...)` + `file.write(...)` | `writeFileStream`, `mkdirp` |

Two maintained options exist: **`saf`** (v2.1.2, published within the last week,
verified publisher, ~2k weekly downloads, 71 likes) and **`saf_util`** +
`saf_stream` (v3.1.0, flutter-cavalry, BSD-3, splits utils from I/O).

**The risk is not capability, it is exposure.** Those download numbers are small.
Expo's SAF module is first-party, widely deployed, and — more to the point —
already proven against *your* users' device matrix: USB OTG drives, SD cards, and
network shares surfaced through third-party DocumentsProviders. Swapping it
re-runs that entire de-risking exercise on a package with a fraction of the
install base. `FileScanner.ts` already carries scar tissue from this
(`MAX_CONCURRENT_DIR_READS`, the `unavailable` carry-over path added in #209).

**Mitigation: this is what C0 exists to test, before any commitment.**

**One silver lining:** `saf_util.stat()` / `list()` return a real `isDir` flag.
That kills the extension-inference hack the current scanner is forced into:

```ts
// SAF entry metadata is unreliable; infer obvious file types by extension.
const isDirectory = !this.isMediaFile(filename) && !NON_DIRECTORY_EXTENSIONS.has(ext);
```

`NON_DIRECTORY_EXTENSIONS` exists purely to limit an always-fails probe, and can
be deleted. (The iOS study reached the same conclusion from the other direction.)

### 2.3 Playback handoff — **not a blocker**

`openMedia.ts` is 61 lines and ports almost verbatim.
[`android_intent_plus`](https://pub.dev/packages/android_intent_plus) (v6.1.0,
fluttercommunity) takes `action`, `data`, `type` and `flags` — the last as a list
of ints, so `FLAG_GRANT_READ_URI_PERMISSION` stays the literal `1` it already is
in the current code. The `MEDIA_MIME_TYPES` map transfers as a Dart const.

Verify on-device that the grant flag actually redelegates a persisted SAF
permission to the external player — that is the whole feature, and it is one of
the first things C0 should prove.

### 2.4 Video thumbnails — take the Kotlin, not the dependency

Currently `expo-video`'s `generateThumbnailsAsync` + `expo-image-manipulator`
(`FileScanner.ts`, `generateThumbnail` / `persistThumbnail`).

The Flutter options are all forks of the abandoned `video_thumbnail`.
`video_thumbnail_gen` (v0.6.3) advertises `content://` SAF support explicitly,
but it is pre-1.0, single-maintainer, and would sit on the critical path of a
core feature.

**Recommendation: write it yourself.** These packages wrap
`MediaMetadataRetriever.setDataSource(context, uri)` — roughly 50 lines of Kotlin
behind a `MethodChannel`, returning a JPEG path. It is the one place in this
migration where a platform channel clearly earns its keep, it removes a fragile
dependency, and it gives you direct control over the `MAX_CONCURRENT_THUMBNAILS`
back-pressure the current scanner already tunes.

### 2.5 User data migration — solvable, but must be designed in from C1

**This is the blocker that is easiest to discover too late.** The app is at
versionCode 62 with real installs. Those users hold state a rewrite would
silently destroy:

| What | Where | Flutter can read it? |
|---|---|---|
| All Redux state (library, overrides, settings, API keys) | SQLite: `/data/user/0/net.nawt.simplemediabrowser/databases/RKStorage`, table `catalystLocalStorage`, key `persist:root` | **Yes** — `sqflite`, read-only |
| `firstTimeSetup` flag | Same table | Yes |
| Poster / thumbnail JPEG caches | `files/smb_posters/`, `smb_thumbnails/` (+ `index.json`), `smb_thumbnails_fs/`, `smb_posters_tvdb/`, `smb_thumbnails_tvdb/`, `smb_audiobook_covers/` | **Yes** — `dart:io`, same sandbox |
| **SAF folder grants** | Held by the OS against the app package | **Yes, they survive** — provided applicationId and signing key are unchanged |

Two details that will bite:

1. **`persist:root` is doubly-encoded.** redux-persist stores a JSON object whose
   *values are themselves JSON strings*, one per slice. Parse twice.
2. **`path_provider` does not point where Expo did.** Expo's `Paths.document` is
   the Android `files/` dir; Flutter's `getApplicationDocumentsDirectory()`
   resolves to a *different* subdirectory of the same sandbox. Construct the
   legacy path explicitly rather than assuming they match — both are readable,
   they are simply not the same folder.

That the **SAF grants survive** is the important one: users would not have to
re-pick their folders. It is a package-level grant, not an app-instance one.
**Verify it on a real device during C0** — the entire migration UX depends on it.

If migration is skipped, every existing user loses their library, their overrides
and their poster cache, and re-scans plus re-hits TMDB from zero. That is the
difference between an update and an unannounced factory reset.

*Escape hatch:* `ImportExportService.exportJson` already produces a full state
snapshot. Worst case, ship an RN release nagging users to export and have the
Flutter build import it — but that depends on users acting, and is a bad enough
UX that it should be the fallback, not the plan.

### 2.6 Flutter does **not** get you iOS for free

This is the most attractive-sounding argument for the migration and it does not
survive contact with `docs/ios-port-feasibility.md`. That study's two hard
blockers are **OS-level, not framework-level**:

- **Persistent folder access** needs security-scoped bookmarks — ~200 lines of
  Swift. In Flutter that is the same ~200 lines of Swift, behind a
  `MethodChannel` instead of an Expo module.
- **MKV/AVI playback** is an AVFoundation codec limitation. Flutter's
  `video_player` is AVPlayer underneath. Identical wall.

Flutter changes who writes the glue, not what the glue must do. If iOS is the
actual goal, the 3–4 week Expo port in that study is the cheaper route by a wide
margin.

### 2.7 Build & release pipeline is replaced, not migrated

Gone: `eas.json`, all three workflows, `build.ps1`, `app.json`'s plugin config,
`expo prebuild`, typed routes, `reactCompiler`. Replaced by a committed
`android/` from `flutter create` plus Gradle. The end state is arguably simpler,
but it is rework — and EAS's managed credentials go away, so the upload keystore
becomes yours to hold in CI secrets.

**Non-negotiable for shipping as an update rather than a new listing:**

- `applicationId` stays `net.nawt.simplemediabrowser`
- Signed with the **same** upload key
- `versionCode` continues monotonically from **62**

Getting any of these wrong strands every existing install on a dead listing.

## 3. Chunks

Sequenced so the expensive, irreversible work is gated behind the cheap answer to
the only question that can kill the project.

### C0 — SAF + platform spike · **2–3 days · throwaway code · GO/NO-GO GATE**

A scratch Flutter app that does nothing but prove the substrate, **on real
hardware with a real library** — not an emulator, and including USB OTG or a
network share if you use them.

Success criteria:

- [ ] Pick a tree; grant persists across a full app restart
- [ ] Recursive walk of the actual library — **wall-clock compared against the current scanner**
- [ ] `isDir` is reported correctly (validating the §2.2 win)
- [ ] Read an `smb.json` as text and a `poster.jpg` as bytes
- [ ] Write a file back into a tree
- [ ] `ACTION_VIEW` + flag `1` opens a `content://` URI in VLC/MX Player
- [ ] `MediaMetadataRetriever` produces a frame from a `content://` URI
- [ ] **A Flutter build with the same applicationId still holds the SAF grants** taken by the RN build (§2.5)
- [ ] `sqflite` opens `RKStorage` and `persist:root` parses

**If the scan is materially slower or flakier than Expo's SAF, stop here.** Three
days is the entire cost of finding that out, versus discovering it in week eight.

### C1 — Scaffolding & release identity · 2–3 days

Only after C0 passes. `flutter create` into a `flutter/` subdirectory so the RN
app stays buildable and shipping alongside it on the same branch. Wire
`applicationId`, signing config and `versionCode` (§2.7) **now**, not at release —
signing surprises are worst when discovered last. Pin every package version. Add
`dart analyze` + `flutter test` to CI next to the existing RN checks.

### C2 — Pure logic, test-first · 2–3 weeks · *the highest-leverage chunk*

Port `SmbTypes`, name normalization, media-file parsing, the override chain and
the provider clients. No UI, no SAF — pure Dart, runs in CI.

**This is where the migration pays for itself, and the trick is to start on the
RN side.** AGENTS.md notes the Jest suite passes vacuously (`--passWithNoTests`).
So:

1. Write Jest tests **against the current TypeScript** capturing the real
   behaviour of `normalizeShowName`, `fuzzyKey`, `buildTmdbSearchQuery` and
   `parseMediaFile` over a table of filenames from your actual library.
2. Port those tests to Dart as the port's specification.

That gives a genuine oracle instead of "looks right," and step 1 has standalone
value in the RN app whether or not the migration proceeds — **the only chunk here
that is not wasted if you stop.**

### C3 — Storage adapter + scanner · 2–3 weeks · *highest complexity*

SAF behind a narrow interface (mirroring the `IStorageAdapter` shape the iOS
study proposes), then `FileScanner`: streaming dispatch, both semaphores
(Dart's `pool` package or a small hand-rolled one), cooperative cancellation,
rescan carry-over, sidecar detection, the `unavailable` flag. Thumbnails via the
C2.4 Kotlin channel.

**ARCHITECTURE.md §7 is the specification for this chunk** — the ordering and
carry-over rules are exactly the kind of thing that breaks subtly and silently.
Re-read §7 step 5 before writing a line of it.

### C4 — State, persistence & legacy import · ~1 week

Riverpod (or Bloc) stores mirroring the two slices. Persistence becomes explicit,
which **deletes the `scanStateTransform` problem entirely** — you choose what to
persist rather than fighting redux-persist's reconciler (ARCHITECTURE.md §5).

Then the §2.5 one-shot `LegacyImport`: read `RKStorage`, convert, adopt the
existing poster/thumbnail directories in place, mark itself done. Test it against
a real device backup of the current app's data directory, not synthetic input.

### C5 — UI · 3–4 weeks · *the bulk*

Order by dependency, cheapest first: `firsttime` → drawer shell + parent lock →
**`MediaBrowserScreen` (1,656 LOC)** → `settings` (1,290) → **`edititem`
(1,695)** → `mergeshows` → `logs`.

Three screens are 4,600 of the ~5,500 UI lines. Everything else is small.

Skip the template leftovers entirely — `(tabs)/`, top-level `index`/`explore`,
`modal.tsx` and the kebab-case component duplicates are dead weight
(ARCHITECTURE.md §15). **The migration is the natural moment to not carry them
across.**

### C6 — Parity pass & staged release · 1–2 weeks

Both builds side-by-side against the same library. Walk the README feature list
as the checklist. Ship to Play's **internal testing track first**, specifically to
validate the §2.5 data migration on real installs before it reaches production —
that path cannot be meaningfully tested any other way.

## 4. Risk table

| Risk | Severity | Notes |
|---|---|---|
| Flutter SAF slower/flakier than Expo's on real storage | **High** | Small-community packages vs. a first-party module already proven on your users' devices. **Wholly mitigated by C0** — three days to a definitive answer. |
| Data migration missed or botched → users lose their libraries | **High** | Fully solvable (§2.5), but only if designed in from C1. Discovering it at C6 means rework across C4. |
| Rewrite stalls half-finished | **High** | Structural (§2.1), not technical. ~12.5k LOC, no shippable midpoint, single maintainer, ~50 commits over 4 months. This is the likeliest failure mode. |
| Behaviour regressions in the scanner | Medium | Intricate ordering/carry-over logic with no existing test suite. Mitigated by C2's test-first approach. |
| Store identity / signing mistake | Medium | Cheap to prevent (C1), expensive to undo — a wrong applicationId or key means a new listing. |
| Pre-1.0 thumbnail dependency | Low | Avoided by writing the Kotlin (§2.4). |
| Playback handoff | Low | Direct port; `android_intent_plus` covers it. |

## 5. The case against — and what to do instead

Every concrete engineering win this migration would deliver is available inside
the RN app for a fraction of the cost:

| Win from migrating | Cheaper route |
|---|---|
| Delete `useKeyboardAwareScroll` (371 LOC) + `react-native-keyboard-controller`; Flutter handles it with `resizeToAvoidBottomInset` | Real, and genuinely nice — but this was *just* fixed in #211/#215. The pain is already paid. |
| Drop `@shopify/flash-list` for natively-virtualized lists | FlashList works. This is a dependency, not a problem. |
| Escape the `scanStateTransform` reconciler hack | ~20 lines of documented workaround, already solved. |
| Real `isDirectory`, delete the extension-inference hack | **Available today** via a storage-adapter refactor — which `docs/ios-port-feasibility.md` M1 already proposes, at ~2–3 days. |
| A real test suite | **C2 step 1 is Jest tests against the existing TypeScript.** You can have this next week without changing frameworks. |
| iOS support | §2.6 — you do not get this. The 3–4 week Expo port is cheaper. |

The current stack is not in the way. Expo SDK 55 is current, the dependency
audit in the iOS study found exactly one Android-only package, CI is green, and
the recent commit history is features and bug fixes — not framework fighting.

**Recommendation:** don't migrate on technical grounds. If you want the wins,
take the storage-adapter refactor and the test suite — the two chunks above that
have standalone value — and keep the RN app.

If the motivation is wanting to build in Dart, that is a perfectly good reason
and this plan is real. In that case: **run C0 anyway.** Three days, and it answers
the only question that can actually stop you.
